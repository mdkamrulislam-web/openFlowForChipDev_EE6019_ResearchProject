KEEP YOUR CIRCUIT

1. Start with the design you already have

Our starting file is shift_register.v. It stores eight bits. Each rising clock edge moves the bits one position towards bit 7 and puts serial_in into bit 0, when enable is 1.

Scroll sideways to explore the diagram ↔
  1. In the extracted folder, open src/shift_register.v with a text editor such as Notepad or VS Code. This is the reusable circuit; it does not contain Tiny Tapeout pin names.
  2. Read its rule: reset wins; otherwise enable shifts; otherwise the stored value stays the same. Reset is synchronous: it takes effect at a rising clock edge.
  3. Try the clock experiment in the HTML guide. From reset, shift in 1, then 0, then 1. Predict the eight-bit output after each edge.

src/shift_register.v
`default_nettype none

// Existing design: 8-bit serial-in, parallel-out shift register.
module shift_register (
    input  wire       clk,
    input  wire       rst,        // 1 clears q on the next rising clock edge
    input  wire       enable,     // 1 shifts; 0 holds the stored value
    input  wire       serial_in,  // new bit enters q[0]
    output reg  [7:0] q
);
    always @(posedge clk) begin
        if (rst)
            q <= 8'b00000000;
        else if (enable)
            q <= {q[6:0], serial_in};
    end
endmodule

RTL — The Verilog description of the circuit’s behaviour and registers.

Predict first: Starting at 00000000, what do inputs 1, 0, 1 produce after three enabled edges?

00000001 → 00000010 → 00000101. A disabled edge keeps 00000101.

THE IMPORTANT ADAPTATION

4. Plan how your signals reach the chip pins

Your circuit has its own signal names. Tiny Tapeout expects a fixed set of ports. A wrapper is a small Verilog module that connects the two.

Scroll sideways to explore the diagram ↔
  1. Use ui_in[0] for serial_in and ui_in[1] for the circuit’s enable. Bits 2–7 are unused.
  2. Connect clk directly. The platform’s rst_n is active low: 0 requests reset. Our circuit’s rst is active high, so connect rst to ~rst_n.
  3. Send all eight q bits to uo_out. We do not use the bidirectional pins: set uio_out and uio_oe to zero. Keep all required wrapper ports.

Port — A named input or output of a Verilog module.

Active low — The function is requested with 0 rather than 1.

Predict first: Is ena the same signal as our shift enable?

No. ena selects this project on the shared chip. Our shift enable is ui_in[1]. This core uses only ui_in[1] to decide whether to shift.

EDIT • src/project.v

5. Add the wrapper around your design

Open the supplied project.v. It creates one instance of your shift register and connects the signals from page 5. The shift-register code itself stays reusable.

  1. Use the complete supplied project.v as the replacement for the template’s example.
  2. For this first run, keep tt_um_student_shift_register unchanged everywhere. For a later submission, choose your own unique name beginning tt_um_ and change all three locations on page 7.
  3. Notice that ~ means invert: ~rst_n converts the reset convention. uio_oe = 0 makes every bidirectional pin an input.
src/project.v
`default_nettype none

// Wrapper: connects the existing design to Tiny Tapeout's fixed ports.
module tt_um_student_shift_register (
    input  wire [7:0] ui_in,
    output wire [7:0] uo_out,
    input  wire [7:0] uio_in,
    output wire [7:0] uio_out,
    output wire [7:0] uio_oe,
    input  wire       ena,
    input  wire       clk,
    input  wire       rst_n
);
    shift_register core (
        .clk       (clk),
        .rst       (~rst_n),  // Tiny Tapeout reset is low; core reset is high
        .enable    (ui_in[1]),
        .serial_in (ui_in[0]),
        .q         (uo_out)
    );

    // Bidirectional pins are unused. A 0 in uio_oe means input direction.
    assign uio_out = 8'b00000000;
    assign uio_oe  = 8'b00000000;

    // ena is Tiny Tapeout's project-selection signal, not shift enable.
    wire _unused = &{ena, ui_in[7:2], uio_in, 1'b0};
endmodule

6. Tell both tools which files to use

The layout builder and simulator read separate source lists. Both must find your core and wrapper. The top module is the outermost circuit the tools should build.

Scroll sideways to explore the diagram ↔
  1. In info.yaml, under project, use top_module: "tt_um_student_shift_register" and source_files: ["project.v", "shift_register.v"]. These filenames refer to files inside src.
  2. In test/Makefile, set PROJECT_SOURCES = project.v shift_register.v. Use the supplied complete Makefile so the surrounding test setup remains intact.
  3. In test/tb.v, the module instantiated as user_project must be tt_um_student_shift_register. The supplied tb.v already does this.

7. Describe the design and its clock

The metadata identifies your project. The datasheet explains how someone can use its pins.

  1. Open the supplied info.yaml. Replace the example author with your name. Keep meaningful title and description text, language Verilog, and the pin labels that match page 5. Keep every required pin key.
  2. Open docs/info.md. Check its How it works, How to test and External hardware sections. It should say: reset clears on an edge; ui_in[1] enables shifting; ui_in[0] supplies the next bit.
  3. For the first exercise keep the supplied 50 MHz target and the current SKY configuration’s 20 ns clock period. The Python test uses 20 ns too. Metadata alone does not change the physical timing constraint.

EDIT • test/test.py

8. Replace the example test with your test

The template’s adder test cannot verify a shift register. Our Python test drives the wrapper’s pins and checks the output after clock edges.

  1. In the extracted folder, open test/test.py. Use this complete file to replace the template’s test/test.py. cocotb is the Python tool that talks to the Verilog simulator.
  2. Read the phases: reset, shift known bits, hold, shift more than eight bits so old data leaves, and reset while enable is 1. It also checks that unused outputs and bidirectional directions stay zero.
  3. For your own design, change the expected result rule and input sequence to match its written behaviour. Keep checks at the external ports so the same test can run on the gate-level circuit.
test/test.py — expected-value rule
# Shift the previous value and add the new bit.
expected = ((expected << 1) | bit) & 0xFF
assert await cycle(bit) == expected

Simulation — Running a model of the circuit before making hardware.

Assertion — A check that stops the test when the observed result differs from the expected one.

Predict first: After shifting 1 eight times from reset, what should the output be? What if enable then becomes 0?

11111111. With enable = 0 it stays 11111111, even when serial_in changes.

BROWSER • ACTIONS → test

10. Check that your shift register passes

Each saved version can start checks. Open the run for the commit that contains your complete adaptation.

  1. Select Actions → test → the run for your final commit. Confirm its branch and commit identifier.
  2. Open the test job and expand Run tests. Read the final test summary: there must be no failures or errors. A green run from before your edit proves nothing about your new design.
  3. If it fails, open the first assertion or compilation error. Fix that cause and save a new commit. The help sheet on page 15 covers common causes.

RTL test — A simulation of your Verilog source before it is converted into physical gates.

Predict first: What does a passing test establish?

The adapted circuit passed the cases and assertions you wrote. It does not prove every possible behaviour, timing corner or manufactured chip.

11. Build, check and look at the layout

The gds workflow turns Verilog into physical gates and wires. The docs workflow builds your datasheet. These run separately from the RTL test.

  2. Open the gds workflow for that commit. Wait for the layout build, precheck, gate-level test and viewer jobs to complete successfully. Job labels can vary; open each job to see what ran.
  3. Open the published Pages/viewer link from the run or repository Deployments. Zoom into the layout. On the gds run’s Summary page, scroll to Artifacts: download tt_submission (layout package) and GDS_logs (reports). Artifact names may change in later templates.

GLS • SAME TEST, GENERATED CIRCUIT

12. See what changes for gate-level simulation

Gate-Level Simulation (GLS) checks the circuit after the tools have converted your Verilog into logic cells. We run the same test at the same external pins.

  1. Keep test/test.py checking ui_in, rst_n and uo_out, as supplied. Internal names such as core.q can disappear when the circuit is built; the chip’s external ports remain the test interface.
  2. Keep the GL_TEST sections in the supplied test/tb.v. Gate-level cells need power connections: VPWR is tied to 1 and VGND to 0 in the simulation fixture.
  3. The gds workflow’s gl_test job downloads the generated netlist and matching SKY130 cell models. It selects the Makefile’s gate-level branch with GATES=yes. The cloud job supplies these dependencies; no local setup is needed.

BROWSER • ACTIONS → gds → gl_test

13. Open the GLS job and check its evidence

The template starts GLS automatically after the GDS build succeeds. A successful RTL test and a successful GDS build do not replace this separate test.

  1. Open Actions → gds → the run for your complete commit. Select gl_test in Jobs. If it is waiting, let gds finish; if it was skipped, inspect the failed build first.
  2. Expand GL test, then Run tests. Read the cocotb summary. Expect PASS with zero failed tests. For this supplied test, the summary should report TESTS=1, PASS=1, FAIL=0. The whole gl_test job must also finish successfully.
  3. Return to the run’s Summary page. Under Artifacts, download gatelevel_test_results. Extract it and open results.xml with a text editor: check for test results with no failure or error entries. Keep the supplied tb.fst or tb.vcd waveform too.
Predict first: Does this GLS result prove that every timing requirement is met?

No. This is a functional gate-level test. Inspect the build’s separate timing reports as well; this walkthrough does not run an SDF timing-annotated simulation.

RTL passes, but GLS fails

Read the first failed assertion. Check reset, the three top-module names and GL_TEST power connections. If necessary inspect the downloaded waveform at the failing time. Compare the same external pins and expected values used by the RTL test.

FINISH • CHECKLIST AND HELP

14. Keep your result and use the guide again

You have finished this exercise when your adapted circuit is tested and its checked layout is archived. Fabrication is a separate later step.

  1. Save the repository URL, commit identifier, test/gds/docs run links, downloaded GDS/reports and datasheet together. Match every item to the same commit.
  2. Use the checklist: pin map agrees; three names agree; two source lists agree; RTL and GLS pass; docs pass; all required gds jobs pass; layout and evidence are saved.
  3. For another existing Verilog design, reuse this route: describe its behaviour, map its pins, wrap it, list its sources and write its tests. For an approved fabrication submission, choose the matching shuttle and follow the submission app’s current checks.
